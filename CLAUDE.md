# CLAUDE.md

`docs/scope.md` is the source of truth for this project; read it before starting any work and follow it over anything here or in your own assumptions. The developer works entirely from an iPad through GitHub Codespaces and Claude Code cloud sessions, so they cannot run desktop apps (no Blender, QGIS, or local viewers); every step must run headless from the `Makefile` or a Python script, and previews happen only through the Codespace's forwarded port 8000 (`make serve`) or the GitHub Pages deploy of `main`. web/index.html always references ./dist/ and ./renders/; local serve and Pages use the identical site/ layout (both built by `make site`). Always keep `dist/base.glb` under 25 MB and the whole `dist/` directory under 60 MB (`make build` checks this), and never require a local GPU for building, rendering, or testing.

Renders are named `renders/NN-slug_YYYY-MM-DD.png`: `NN` is the camera number (01–20), `slug` is the camera name from `cameras.json` slugified (lowercase, hyphens), and the date is the data date, defined as `max(last_checked)` in `data/proposals.csv` at render time (not the day the render was made). `make renders-check` parses that date from each filename and flags any render older than the current data date.

Towers finished after the LiDAR survey (they show up as ground, a stump or a podium) are entered in `data/proposals.csv` as `status: existing` rows, with a footprint in `data/proposals.geojson` and the official height. `make build` hides every base building under that footprint, so the official height replaces the measured one; P001 Stantec Tower is the example (LiDAR 189 m → official 250.8 m). Don't patch heights in `fetch_base.py` or `base.glb` for this. The hidden-building lists are tied to the exact `dist/base.glb`, so `make build` must run after every `make fetch` (the Makefile does this).

Camera views live in `data/cameras.json` and are generated by `make cameras` (`scripts/set_cameras.py`, landmark coordinates plus bearing/height/pitch). `make contact-sheet` renders all 20 headlessly through the real viewer (Playwright + SwiftShader, no GPU) into `docs/contact-sheet/` and `docs/contact-sheet.png`; check it after any camera or look change.

## Height, status and placement rules (decided by Mark, Phase 3C)

Apply these to every row; `scripts/promote_candidates.py` (`phase3c()`) and `scripts/auto_footprints.py` implement them, and every change they make is logged in `docs/promotion-log.md`.

- Area-wide rezonings (a zone ceiling laid over many lots) stay dropped.
- SkyriseCities scheme above the DC or zone ceiling: if the project's forum shows activity in the last 24 months ("Last Post" on its project page), the scheme is the proposal: use its storeys and height, confidence medium, `height_source` noting "exceeds current DC; scheme per SkyriseCities". If it is older than 24 months with no activity, keep the DC or zone value and note the stale scheme. Read a DC's real ceiling, not its sunset fallback ("in the event that the owner does not obtain a permit by …").
- `status = construction` never renders as an envelope (`make build` fails on it). Resolve a low-confidence construction row from SkyriseCities, the DP text or the building-permit descriptions (`24uj-dj8v`), and set confidence to at least medium with the best estimate. If the permit's storeys fall below the inclusion rule, the row is removed.
- Stadium Yards (P009) is removed: 6 storeys in node Other is below the rule.
- Multi-tower rows use per-tower heights when known (P011: 16 / 19 / 21 storeys). They are stored as `part_heights` on the GeoJSON feature, and `height_m` stays the tallest.
- Placement: a single tower from a development permit is centred on the permit's coordinate, still clipped to the lot. A row flagged as on a park first checks the OSM tags: vacant land tagged grass or greenfield is not a park. If it is a genuine park, the footprint is moved off it when the permit coordinate is outside the park. If the lot itself is in a park, the flag stays.
